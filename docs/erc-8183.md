# Optional ERC-8183 job infrastructure

Local prototype for Ink developers. Not deployed or audited. `Four02JobEscrow` is
independent of `BountyEscrow`, the marketplace API, and `Four02SpendingPermissions`.
Existing contracts and their deployments do not change. There is no automatic
integration with an external agent platform, marketplace, evaluator or indexer.

The official draft's embedded sample itself differs from its prose: it restricts
budget setting to providers, omits `expectedBudget` from `fund`, and permits
zero-budget Open submissions. This profile follows the prose on all three:
client **or** provider may set budget, funding binds the expected amount, and a
positive funded budget is required before submission.

The separately evolving repository uses different selectors (`uint48` expiry,
provider agent ID, token/optional parameters), per-job tokens, evaluator/platform
fees, hooks, administrative controls, claims and an evaluation grace period.
Those behaviors and ABIs are **not** supported here. Its Open expiry and
zero-budget submission paths are not imported. The SDK is for this exact profile;
it is not a drop-in SDK for every contract called ERC-8183. Recheck the draft and
make a deliberate versioned change before adopting any future revision.

This is a **draft-targeting implementation with restrictions**, not a blanket
ERC-8183 compliance certification. The extra deadline guards and party/token
restrictions below must be reviewed before claiming compatibility with another
implementation. Optional hook/fee/reputation/relay features are deliberately absent.

## Roles and lifecycle

The buyer is the standard's **client**. The client creates a job and approves and
funds its budget. The **provider** performs work and submits a `bytes32`
commitment. The immutable **evaluator** decides whether that work merits payment.
Addresses need no 402 registration, agent identity, or reputation enrollment.
Evaluator may equal client (buyer decides); other role overlaps are allowed, so
provider=evaluator allows self-approval. Choose and verify these roles off-chain.
The zero provider is allowed only until the client assigns it once, while Open.
The escrow and payment token addresses cannot be participants.

| State / action | Authorized caller | Result and funds |
| --- | --- | --- |
| Create | Client | Open, evaluator nonzero, expiry strictly in future |
| Open / setProvider | Client | Fill a zero provider once with a nonzero address |
| Open / setBudget | Client or assigned provider | Replace quoted budget (zero is allowed here) |
| Open / fund(expectedBudget) | Client | Funded; pull exactly positive budget from client; provider required; quote must match |
| Open / reject(reason) | Client | Rejected; no token movement, even if budget was quoted |
| Funded / submit(deliverable) | Provider | Submitted; no token movement |
| Submitted / complete(reason) | Evaluator | Completed; full budget to provider |
| Funded or Submitted / reject(reason) | Evaluator | Rejected; full budget to client |
| Funded or Submitted / claimRefund | Anyone at/after expiry | Expired; full budget to client |

No other transition is valid. Completed, Rejected and Expired are terminal;
settlement cannot be repeated. Job IDs start at 1 and unknown IDs revert.
Descriptions live in job storage. Deliverable and reason commitments are emitted
in events, not interpreted or fetched. Zero commitments are allowed. A hash does
not prove delivery quality, content availability, or an honest evaluation.

**Explicit deadline policy:** funding, submission and completion require
`block.timestamp < expiredAt`. At equality, refund is immediately available in
Funded and Submitted with no grace period. This adds a hard completion cutoff to
the draft prose, which leaves the post-expiry completion race unspecified; the
embedded sample permits completion until a refund wins. Integrators must accept
this stricter profile. Evaluator rejection after expiry is still allowed and
refunds the same full amount. Open jobs do not expire on-chain; the client may
reject them, and Open budget/provider edits do not extend their immutable expiry.
Time passage alone never changes status or sends a transaction: someone must
call `claimRefund`. Allow sufficient time for both work and evaluation.

## Token accounting and trust

The constructor takes one immutable ERC-20 token contract. On Ink the intended
token is native USDC (`0x2D270e6886d130D724215A266106e6832161EAEd`, six decimals);
local examples use a mock. There is no hardcoded live escrow address. Deployment
selection and token verification are the integrator's responsibility.

SafeERC20 plus exact sender/recipient balance checks protect funding, payouts and
refunds. False returns, reverting transfers, silent no-ops and transfer taxes
revert the entire action, restoring state and accounting. Reentrancy guards cover
all mutations. Rebasing, taxed, malicious or otherwise non-exact tokens are
unsupported. Balance checks cannot make an arbitrary malicious token honest;
USDC freezing/pausing can still block settlement and refunds until token transfers
resume. There is no administrator, rescue function, proxy, fee, partial payment,
arbitration, evaluator replacement or emergency bypass.

`totalEscrowed` is exactly the sum of Funded and Submitted budgets. With a supported
token, balance is at least that liability; unsolicited transfers are surplus,
never funding or someone else's withdrawable budget. **Do not send tokens directly
to the escrow**: they are unrecoverable by this implementation. `fund` must pull
the budget from the client even if a surplus exists.

Existing spending permissions authorize bounded USDC transfers only. Paying the
escrow address through them does not call `fund`, select a job, bind its quote, or
change its status. No adapter or shortcut has been added. A future delegated
funding mechanism needs explicit authority bound to chain, escrow, job, client,
token and budget, plus an atomic funding call and its own security review.

The evaluator can approve bad work, reject good work, or stay silent. A client
acting as evaluator has unilateral decision power; an absent evaluator exposes
the provider to nonpayment at expiry. This contract enforces their decision and
deadlines, not fairness. Agree on evaluator policy and deadline before funding.

## ABI and SDK

Core signatures omit optional hooks/parameters entirely:

```solidity
createJob(address provider, address evaluator, uint256 expiredAt, string description) returns (uint256)
setProvider(uint256 jobId, address provider)
setBudget(uint256 jobId, uint256 amount)
fund(uint256 jobId, uint256 expectedBudget)
submit(uint256 jobId, bytes32 deliverable)
complete(uint256 jobId, bytes32 reason)
reject(uint256 jobId, bytes32 reason)
claimRefund(uint256 jobId)
```

Use `packages/job-escrow` for unsigned calls, exact approval/funding plans,
deployment compatibility checks, job reads, and receipt parsing. Verify the
deployed source separately: a matching profile string is not code verification.
Amounts are bigint token base units. Each plan specifies chain and caller; the
integrator must enforce those fields when signing, simulate again, and wait for
successful receipts. An approval and fund are separate transactions; a changed
budget causes fund to revert. Revoke leftover allowance if abandoning that plan.

See `examples/erc8183-local.ts` for an external buyer/provider/evaluator lifecycle
using three separate local wallets, without any marketplace service. Run from
the repository root after installing dependencies:

```sh
forge build
npm run example:erc8183
```

The example starts its own loopback Anvil with disposable keys and a mock token;
it accepts no production RPC or private key. The SDK itself never signs, submits,
deploys, calls external services, or accesses environment keys.

| Draft requirement or explicit profile rule | Local evidence |
| --- | --- |
| Six states, authorized transitions, terminal finality | `test_allRolesAllStatesAllActions`: 6 states × 4 callers × 7 actions; `test_unknownIdsRevertEveryAction` |
| Client creation, nonzero evaluator, future expiry, optional provider | `test_createAndLateAssignmentEvents`, `test_creationValidationAndNoFiveMinuteMinimum` |

| Provider submission, evaluator completion, exact full payout and events | `test_fullBudgetCompletionAndEvidenceEvents`, local three-wallet example |
| Open client rejection, funded/submitted evaluator refunds | `test_rejectionInAllThreeStatesPaysOnlyFundedBudget`, `test_postExpiryRejectionAndOpenEdits` |
| Permissionless refund at timestamp equality in both funded states | `test_expiryBoundaryAndNoCompletionRefundRace`, local example |
| Additional hard cutoff (profile restriction, not a draft requirement) | `test_expiryBoundaryAndNoCompletionRefundRace` |
| Safe transfers and reentrancy protection | Missing allowance/balance, false/no-op/revert/tax transfer rollback, payout/refund retry and reentrancy tests |
| No direct-transfer funding shortcut | `test_spendingPermissionTransferIsNotJobFunding` |
| Exact per-job accounting and surplus isolation | `testFuzz_independentJobsConserveExactBudgets`, two stateful invariants in `Four02JobEscrowInvariant.t.sol` |
| SDK selectors, exact approvals, role/quote checks and evidence | `packages/job-escrow/test/sdk.test.ts`, ABI artifact comparison, local example |

These tests establish the implemented behavior and its regression coverage, not
an audit, economic safety guarantee, or proof of interoperability with other drafts.
