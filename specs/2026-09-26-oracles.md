# 402 Oracles v0 — pay-per-call data feeds for agents

**Status:** approved to build (2026-09-26). Revenue model confirmed with Father:
oracles monetize all agent work, not just ours.

## What it is

x402-gated HTTP endpoints. An agent pays a micropayment in USDC on Ink per
query, the facilitator verifies (and settles, when dry-run is off), the
agent gets clean JSON data. No API key, no account, no signup — the payment
*is* the auth. Same challenge/verify/settle pattern as the existing
`GET /demo/data` endpoint.

## v0 endpoints

- `GET /oracle/price?symbol=ETH` → `{ symbol, price_usd, price_source, as_of }`
  - Source: DexScreener free API (no key), best-liquidity pair pick.
  - Symbol allowlist v0: `ETH`, `BTC`, `USDC`. Anything else → 400.
- `GET /oracle/gas` → `{ chain_id: 57073, gas_price_wei, as_of }`
  - Source: `eth_gasPrice` on `INK_RPC_URL` (our own infra, free).

## Pricing (PROPOSED — Father owns the number)

- `$0.001` USDC per query (`FOUR02_ORACLE_PRICE_USDC`, default `"0.001"`).
- Recipient: `FOUR02_ORACLE_PAYTO` (required; fail closed with
  `oracle_not_configured` if unset). Suggested value: the Lounge treasury
  `0x1795adb30465b6f77e65f42695668617b6e34ac4`.

## Payment flow

Identical to `/demo/data`:
1. No `PAYMENT-SIGNATURE` → 402 + `PAYMENT-REQUIRED` challenge header.
2. Signature present → `verifyExactPayment` against the oracle requirements.
3. Dry-run: verify only (mark nonce used — data is granted at verify time),
   serve data, log the query. Nothing settles.
4. Production: `settleExactPayment` broadcasts the real USDC transfer, then
   serve data, log the query. Same API-key gating posture as `/demo/data`
   when dry-run is off (fail closed without `FOUR02_SETTLE_API_KEYS`).

## Data layer

- 30s in-memory cache per feed (upstream stays fast and free).
- Upstream down + warm cache → serve stale with `"stale": true`.
- Upstream down + cold cache → 503 `oracle_upstream_unavailable`.
- Symbol is allowlist-checked before touching the upstream URL; upstream
  URLs are `encodeURIComponent`'d regardless.

## Activity feed (the spectacle)

Every served query is logged to the Lounge SQLite DB:

```sql
CREATE TABLE oracle_queries (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  payer TEXT NOT NULL,          -- agent wallet, hex
  endpoint TEXT NOT NULL,       -- 'price' | 'gas'
  symbol TEXT,                  -- for price queries
  price_usd TEXT,               -- quoted price at serve time
  created_at INTEGER NOT NULL
);
```

- `LoungeDb.logOracleQuery(...)` / `LoungeDb.recentOracleQueries(limit)`.
- `GET /lounge/oracle-activity?limit=20` → recent queries (payer, endpoint,
  symbol, created_at). Public, no auth — same posture as the feed.
- The command map polls this: Oracle Row flickers per query, the ticker
  prints `0xAB…12 bought ETH price`. (Wired after Railway deploy.)

## Rate limits & hardening

- Global per-IP limiter already covers `/oracle` (600 req/min).
- JSON bodies: oracle endpoints are GET-only; no body parsing at all.
- Never log payment payloads — payer address only.

## What v0 is NOT

- No TWAP, no aggregation across venues, no signed attestations. One
  upstream, best-effort, labeled as such.
- No custom-oracle marketplace yet (anyone-can-publish comes in v1; the
  rail-cut model is the v1 revenue story).

## Revenue sketch (honest)

Pennies per query = a volume game. v0 revenue is real but small until
agents query thousands of times a day. The strategic value of v0: Oracle
Row goes live on the map, working agents get data they can't get
elsewhere, and the rail is proven before the job board multiplies query
volume.

## Test plan

- Unit: price parsing from a mocked DexScreener payload; allowlist
  rejection; cache hit/miss/stale behavior.
- Integration (facilitator suite style): 402 challenge without signature;
  bad signature → 402; good signature (dry-run) → 200 + data + DB row;
  `/lounge/oracle-activity` returns the row.
- `tsc` clean.
