# 402 Nado x402 — pay-per-call Nado market data for agents

**Status:** spec for Father's review (2026-09-26). Builds on the approved
Oracles v0 pattern; nothing is implemented yet.

## What it is

x402-gated HTTP endpoints in front of Nado's public read APIs. An agent
pays a micropayment in USDC on Ink per query, the facilitator verifies
(and settles, when dry-run is off), the agent gets clean Nado market JSON.
No API key, no account, no signup — the payment *is* the auth. Same
challenge/verify/settle pipeline as `GET /oracle/price` and `/demo/data`.

Why Nado: it is the dominant DEX on Ink (~$8.5B 30d perp volume) with an
official public REST surface and no key requirement on reads. Agents get
Ink-native perp data (funding rates, orderbook depth, mark/index prices)
they cannot get from DexScreener-style aggregators.

## v0 endpoints

All under the facilitator, mirroring the oracle route style.

- `GET /nado/markets` → `{ markets: [{ product_id, ticker_id, base, quote, product_type }], as_of }`
  - Upstream: `GET {NADO_GATEWAY}/v2/pairs` (cost weight 1, no params).
  - No params. This is the discovery endpoint agents use to learn valid
    `market` values.
- `GET /nado/ticker?market=BTC-PERP` → `{ ticker_id, last_price, base_volume, quote_volume, price_change_percent_24h, stale, as_of }`
  - Upstream: `GET {NADO_ARCHIVE}/v2/tickers` (cost weight 1, no params),
    filtered server-side by resolved `ticker_id`.
- `GET /nado/orderbook?market=BTC-PERP&depth=20` → `{ ticker_id, bids: [[price, size], ...], asks: [...], stale, as_of }`
  - Upstream: `GET {NADO_GATEWAY}/v2/orderbook?ticker_id=…&depth=…`
    (cost weight 1). `depth` default 20, max 100.
- `GET /nado/funding?market=BTC-PERP` → `{ ticker_id, funding_rate, mark_price, index_price, open_interest, open_interest_usd, next_funding_ts, stale, as_of }`
  - Upstream: `GET {NADO_ARCHIVE}/v2/contracts` (cost weight 1, no params),
    filtered server-side by resolved `ticker_id`. Perp markets only —
    spot `market` values → 400 `funding_perp_only`.
- `GET /nado/candles?market=BTC-PERP&timeframe=1h&limit=50` → `{ ticker_id, timeframe, candles: [[ts, o, h, l, c, v], ...], stale, as_of }`
  - Upstream: `POST {NADO_ARCHIVE_V1}` body
    `{"candlesticks": {"product_id": N, "granularity": 3600, "limit": 50}}`
    (cost weight `2 + limit/100`). `timeframe` allowlist:
    `1m 5m 15m 1h 4h 1d`; `limit` default 50, max 200.

### Market parameter

`market` accepts `BTC-PERP`, `BTC`, or `BTC-PERP_USDT0` (case-insensitive)
and resolves to Nado's `ticker_id` via the cached `/nado/markets` list
(spot products have even IDs, perps odd; quote is `USDT0`). Unknown market
→ 400 `unsupported_market` with the valid list hint. Resolution happens
*before* the payment challenge so agents don't pay for a typo.

## Pricing (PROPOSED — Father owns the number)

Two tiers, reflecting upstream cost asymmetry (orderbook hits the live
sequencer; candles hit the indexer with weight `2 + limit/100`):

- Light reads — `markets`, `ticker`, `funding`: `$0.001` USDC
  (`FOUR02_NADO_PRICE_USDC`, default `"0.001"`). Matches oracles v0.
- Heavy reads — `orderbook`, `candles`: `$0.002` USDC
  (`FOUR02_NADO_HEAVY_PRICE_USDC`, default `"0.002"`).
- Recipient: `FOUR02_NADO_PAYTO` (required; fail closed with
  `nado_not_configured` if unset). Suggested value: the Lounge treasury
  `0x1795adb30465b6f77e65f42695668617b6e34ac4` (same as oracles).

## Payment flow

Identical to `/oracle/price`:
1. No `PAYMENT-SIGNATURE` → 402 + `PAYMENT-REQUIRED` challenge header.
2. Signature present → `verifyExactPayment` against the tier requirements
   for the endpoint being called.
3. Dry-run: verify only (nonce consumed at verify time — one signature
   buys one query), serve data, log the query. Nothing settles.
4. Production: `settleExactPayment` broadcasts the real USDC transfer, then
   serve data, log the query. Same API-key gating posture as oracles when
   dry-run is off (fail closed without `FOUR02_SETTLE_API_KEYS`).

## Data layer

- Upstream base URLs (unified endpoints, recommended for new
  integrations): gateway `https://api.prod.nado.xyz/gateway/v2`, archive
  `https://api.prod.nado.xyz/archive/v2`, archive v1
  `https://api.prod.nado.xyz/archive/v1`. Configurable via
  `FOUR02_NADO_GATEWAY_URL` / `FOUR02_NADO_ARCHIVE_URL`. 8s fetch timeout,
  same as oracles.
- Per-endpoint in-memory cache + stale fallback (same semantics as
  oracles: fresh hit served, miss fetches, upstream failure serves stale
  with `"stale": true`, cold failure → 503 `nado_upstream_unavailable`):

  | endpoint   | TTL | why |
  |------------|-----|-----|
  | markets    | 300s | changes only on listings |
  | ticker     | 15s | fast-moving 24h stats |
  | orderbook  | 5s  | live book, goes stale fast |
  | funding    | 30s | funding updates on a schedule, not tick-by-tick |
  | candles    | 60s | indexer data, cheap to re-serve |

- `market` is allowlist-resolved before touching upstream; all upstream
  params are `encodeURIComponent`'d; numeric params are clamped
  (`depth ≤ 100`, `limit ≤ 200`).

## Activity feed (the spectacle)

Reuse the existing `oracle_queries` table — Nado queries show up in the
command-map ticker with zero new plumbing:

- `endpoint`: `'nado_markets' | 'nado_ticker' | 'nado_orderbook' | 'nado_funding' | 'nado_candles'`
- `symbol`: the resolved `ticker_id` (e.g. `BTC-PERP_USDT0`)
- `price_usd`: quoted `last_price` / `mark_price` at serve time where the
  endpoint has one, else NULL
- `GET /lounge/oracle-activity` returns them unchanged; the ticker prints
  `0xAB…12 bought BTC-PERP funding`.

## Auth / rate-limit handling (upstream)

- Nado reads need **no API key** — queries are IP-based only: 2400 weight
  per minute / 400 per 10s on gateway and archive (ccxt confirms
  `requiredCredentials.apiKey: false` for public endpoints).
- Our caching keeps facilitator egress far under budget: worst realistic
  case (every endpoint at TTL expiry, weight ≤ 2) is single-digit
  weight/min against a 2400 budget. Railway's shared egress IP is noted
  as the one watch item — if 429s appear, we serve stale and log it.
- Upstream 429 → treat like any upstream failure: stale cache if warm,
  else 503 `nado_upstream_unavailable` (with `detail: "rate_limited"` so
  it shows up distinctly in logs).
- Never log payment payloads — payer address only. Never forward caller
  headers upstream.

## What v0 is NOT

- No writes. Orders stay in Nado's own MCP/CLI under their
  human-confirmation ritual — 402 does not touch order placement.
- No subaccount-gated reads (balances, positions, open orders): those need
  the caller's wallet key and don't fit pay-per-call.
- No websocket subscriptions — request/response only.
- No cross-venue aggregation. One upstream (Nado), labeled as such.

## Revenue sketch (honest)

Same pennies-per-query volume game as oracles, but the data is
differentiated: Ink-native perp funding and orderbook depth aren't on
DexScreener. Trading agents are the hungriest repeat queriers — a bot
checking funding every minute is 1,440 paid queries a day. The strategic
value: Nado is the first outside protocol on the 402 rail, which is the
pitch to the next ten.

## Test plan

- Unit (mocked fetch, no network): `ticker_id` resolution incl.
  case-insensitivity and `unsupported_market`; response parsing per
  endpoint (tickers/contracts/orderbook/candles fixtures from ccxt's
  documented shapes); cache hit/miss/stale per TTL; param clamping
  (`depth=500` → 100, `limit=500` → 200, bad `timeframe` → 400);
  `funding_perp_only` rejection for spot markets.
- Integration (facilitator suite style): 402 challenge without signature;
  bad signature → 402; good signature (dry-run) → 200 + data + DB row in
  `oracle_queries` with the `nado_*` endpoint; `/lounge/oracle-activity`
  returns the row.
- No mainnet, no real Nado calls in tests, no real payments. `tsc` clean.
